# SkySend: восстановление WordPress в существующем jail `www`

Это полный пакет **сайта**, а не образ Ubuntu и не установщик всего сервера.
Развёртывание выполняет администратор компании. Автор сайта не подключается
к `gw1.isg.dev` и не меняет общую инфраструктуру.

В пакете:

- `site/` — ядро WordPress 7.1.1, медиатека, русские переводы, активная тема
  Twenty Twenty-Five 1.5, Carousel Slider Block 2.1.5, SEOPress Free 10.2
  и WP Super Cache 3.1.3;
- `database.sql` — актуальная база сайта: страницы и ревизии, изображения,
  шапка, футер, меню, шаблоны, стили, SEO и настройки плагинов;
- `robots-production.txt` — robots для `https://skysend.ru`;
- `manifest.json` — версии, дата снимка, хеши и результаты проверки;
- `SHA256SUMS` и `verify-package.php` — проверка файлов после распаковки;
- эта инструкция.

**Рабочего `wp-config.php` нет.** В `site/wp-config-sample.php` только стандартные
заглушки WordPress. Пароли сервера, БД, GitHub и SSH не передаются. Пароли всех
скопированных аккаунтов WordPress заменены случайными неизвестными значениями;
сессии, application passwords и ключи восстановления очищены **только в копии**.
Ключ IndexNow исходной ВМ также очищен, автоматическая отправка IndexNow отключена;
при необходимости компания включит её со своим ключом после публикации.
Администратор задаёт новый пароль после импорта. Пользователи/авторство сохранены.
Неактивная старая тема SkySend, готовые файлы кеша, cache drop-ins, логи и серверные
конфигурации Ubuntu не включены: функциональный сайт полный, резервная копия ОС — нет.
Страничный кеш активируется на целевом сервере **после** смены URL и проверки сайта,
чтобы в него не попали адреса исходной ВМ.

Архив и SQL конфиденциальны: база содержит учётки, email, черновики и историю.
Передавать адресно закрытым каналом. Не выкладывать в публичный каталог, GitHub
или FTP-листинг `https://gw1.isg.dev/`, не распаковывать весь пакет в webroot.

### Если предыдущий пакет уже развёрнут

Пакет от 24.09.2026 содержит полный новый снимок, а не SQL-патч. Не копировать его
поверх работающего docroot и не импортировать `database.sql` в непустую базу.
Сначала сохранить текущий сайт, затем восстановить новый пакет рядом — в новые
каталог и БД с суффиксом `20260924`. После проверки переключить только vhost/upstream,
а прежние каталог и БД оставить для отката. Если после 24.09 на целевом сайте уже
вносились собственные правки, их нужно сверить и перенести до переключения. Точное
время снимка указано в `manifest.json` (`createdAtUtc`); правки после этого времени
в новый пакет не входят.

## 1. Согласовать параметры и сохранить возможность отката

Сначала определить у администратора:

- фактический docroot внутри `www`, PHP-пользователя/пул, расположение vhost;
- где находится MySQL/MariaDB и какой DBHOST доступен из jail;
- где завершается HTTPS: Apache в jail или внешний прокси;
- основной домен: в примерах **https://skysend.ru**, www перенаправляется на него;
- IP внешней точки входа и кто переключает DNS/прокси.

Сохранить старый SkySend, его БД, конфигурации домена/прокси и прежние DNS-записи.
Новый сайт готовить в **отдельных новых каталоге и БД**, не поверх соседнего сайта.
На время окончательного снимка/приёмки остановить редакторские правки либо запросить
новый пакет: этот архив не содержит изменений, внесённых после его даты.

Не запускать старые `install-jail.sh`, `install-wordpress.sh`, первоначальный
native-import, сборщик блоков или configure-seo. Не обновлять общие пакеты PHP,
Apache и БД ради этого архива. Не останавливать и не перезапускать весь jail.

## 2. Проверить окружение (только чтение)

На FreeBSD-хосте:

```sh
jls -j www -n jid name path ip4.addr ip6.addr
jexec www freebsd-version -u
jexec www php -v
jexec www php -m
```

Войти в shell jail по принятому в компании порядку, например `jexec www /bin/sh`.
Дальнейшие пути и команды — **внутри jail**, не на хосте. PHP CLI и PHP веб-сервера
могут иметь разные настройки; проверить оба. Нужны mysqli, curl, mbstring,
XML/DOM/SimpleXML, ZIP и обработка изображений GD или Imagick; intl рекомендуется.
Рекомендуемое окружение WordPress: PHP 8.3+, MariaDB 10.11+ или MySQL 8.0+, HTTPS.
Это рекомендации, а не требование переустановить уже совместимые службы.

Для команд ниже нужен WP-CLI. Если `wp` отсутствует, использовать официальный
WP-CLI в закрытом служебном каталоге, не webroot; глобальная установка не обязательна.
Ссылки: [требования WordPress](https://wordpress.org/about/requirements/),
[установка WP-CLI](https://wp-cli.org/#installing).

## 3. Распаковать в закрытый каталог и проверить целостность

Проверить SHA-256 ZIP по отдельно переданной контрольной сумме (`sha256 archive.zip`
на FreeBSD, `Get-FileHash` на Windows). Создать закрытый каталог, например
`/root/skysend-delivery`; архив и SQL хранить там с правами 0600, каталог 0700.
Если используется не root, выбрать закрытый каталог того же администратора.

Распаковать ZIP туда средствами `unzip` или `bsdtar`. В нём один верхний каталог
`skysend-wordpress-YYYYMMDD`. Войти в этот каталог:

```sh
php verify-package.php
```

Ожидается `OK: ... files verified.` При несовпадении файлов остановиться и запросить
исходный архив. `SHA256SUMS` имеет GNU-формат, поэтому на FreeBSD используйте
предоставленную PHP-проверку, а не предполагайте совместимость `sha256 -c`.

## 4. Скопировать только `site/` в новый docroot

Следующие значения — **примеры**, администратор заменяет их на согласованные.
`PACKAGE` должен указывать на распакованный каталог с `database.sql` и `site/`.
Все переменные принадлежат только текущей shell-сессии:

```sh
PACKAGE='/root/skysend-delivery/skysend-wordpress-20260924_HHMMSS'
DOCROOT='/usr/local/www/skysend-new-20260924'
DBNAME='skysend_20260924'
DBUSER='skysend_20260924'
DBHOST='localhost'
NEW_URL='https://skysend.ru'
```

В `PACKAGE` заменить `HHMMSS` на время из имени фактически распакованного каталога.
Если пакет ставится сначала на `https://new.skysend.ru`, заменить `NEW_URL` именно
на этот адрес; robots для основного домена применять только при финальном
переключении. Перед сменой домена снова выполнить безопасный `wp search-replace`.

Убедиться, что новый docroot не существует; если существует — не продолжать,
а выбрать новый путь. Не удалять существующий каталог для удобства.

```sh
test ! -e "$DOCROOT"
```

Только после успешной проверки:

```sh
mkdir -p "$DOCROOT"
cp -a "$PACKAGE/site/." "$DOCROOT/"
```

SQL, manifest, инструкция и `verify-package.php` **не копируются** в docroot.
Права/владельца сразу привести к локальной политике отдельного сайта (шаг 8).
До настройки PHP и защиты конфигурации не публиковать этот каталог.

## 5. Создать отдельную пустую БД и нового `wp-config.php`

Через инструмент DBA создать `DBNAME` с utf8mb4/совместимой collation
`utf8mb4_unicode_ci` и выделить `DBUSER` только для этой базы. Не давать права
на другие сайты. Если БД внешняя, доступ разрешается с адреса PHP/jail, а не всем
хостам. Пароль генерирует и хранит компания; он отсутствует в архиве.

SQL предназначен для **пустой** БД и не содержит DROP TABLE, CREATE DATABASE,
глобальных пользователей или GRANT. Если выбранная БД не пуста, остановиться.
Префикс в этом пакете: **`wp_`**, подтверждение в `manifest.json`.

Создать конфигурацию. Пароль вводится по запросу, не в истории команд:

```sh
wp --path="$DOCROOT" config create \
  --dbname="$DBNAME" --dbuser="$DBUSER" --dbhost="$DBHOST" \
  --dbprefix=wp_ --dbcharset=utf8mb4 --locale=ru_RU --quiet --prompt=dbpass
wp --path="$DOCROOT" config set DISALLOW_FILE_EDIT true --raw
wp --path="$DOCROOT" config set WP_DEBUG false --raw
wp --path="$DOCROOT" config set WP_ENVIRONMENT_TYPE production
```

`--quiet` также не даёт WP-CLI вывести повторно собранную команду с паролем.
Команда создаёт новые salts. Не копировать config с тестовой ВМ, не применять
`--force`, `--skip-salts` или `--insecure`. Не устанавливать ядро заново:
оно уже включено. Не выполнять `wp core install`, чтобы не создать другую БД сайта.

Команды WP-CLI предпочтительно выполняются от выделенного пользователя сайта.
Если администратор намеренно использует root, к вызовам `wp` потребуется
`--allow-root`. Это не разрешение менять соседние сайты.
При `PACKAGE` в закрытом `/root` импорт выполняет администратор-root с
`--allow-root`. Для другого CLI-пользователя пакет хранить в его собственном
закрытом каталоге; не открывать SQL всем через 0755/0644 ради импорта.

## 6. Импортировать базу, заменить адреса и задать новый пароль

Перед импортом проверить, что выбран именно новый конфиг/DBNAME:

```sh
wp --path="$DOCROOT" config get DB_NAME
wp --path="$DOCROOT" db query 'SHOW TABLES' --skip-column-names
```

Первая команда должна показать новое имя, вторая — отсутствие таблиц. Только затем:

```sh
wp --path="$DOCROOT" db import "$PACKAGE/database.sql"
wp --path="$DOCROOT" db check
wp --path="$DOCROOT" option update blog_public 0
```

До приёмки использовать закрытый тестовый vhost/ограничение доступа. `blog_public=0`
не заменяет HTTP-аутентификацию и не защищает SQL-файлы. Пока индексация отключена,
нативные XML-карты могут быть недоступны — это ожидаемо; итоговую SEO-проверку
делать после возвращения `blog_public=1` в шаге 11.

В дампе URL сохранён как на исходной ВМ — **http://31.129.98.28**. Сначала пробная
замена, затем реальная. WP-CLI сохраняет сериализацию и ID:

```sh
wp --path="$DOCROOT" search-replace 'http://31.129.98.28' "$NEW_URL" \
  --all-tables-with-prefix --skip-columns=guid --precise --report-changed-only --dry-run
```

Проверить отчёт и имя выбранной базы. Если всё соответствует новой установке:

```sh
wp --path="$DOCROOT" search-replace 'http://31.129.98.28' "$NEW_URL" \
  --all-tables-with-prefix --skip-columns=guid --precise --report-changed-only
wp --path="$DOCROOT" option update home "$NEW_URL"
wp --path="$DOCROOT" option update siteurl "$NEW_URL"
wp --path="$DOCROOT" rewrite flush
```

Не использовать `--all-tables` при замене, обычный find/replace в SQL или
`rewrite flush --hard`: последнее может перезаписать старые 301 в `.htaccess`.
Старый IP в колонке `guid` допустим и намеренно сохраняется; в src/href/canonical
и SEO-настройках старого IP оставаться не должно.

Задать новый пароль скопированному администратору:

```sh
wp --path="$DOCROOT" user update skysend_admin --quiet --prompt=user_pass
```

Пароль тестовой ВМ в этом пакете не работает. При необходимости компания создаёт
свой администраторский аккаунт; исходного пользователя не удалять вместе с его
материалами. Проверить/заменить административный email в настройках WordPress.
Другие скопированные аккаунты также требуют нового пароля перед использованием.

## 7. Проверить версии и сохранить готовые настройки

```sh
wp --path="$DOCROOT" core version
wp --path="$DOCROOT" core verify-checksums --version=7.1.1 --locale=en_US
wp --path="$DOCROOT" theme list
wp --path="$DOCROOT" plugin list
wp --path="$DOCROOT" plugin verify-checksums carousel-block wp-seopress wp-super-cache
wp --path="$DOCROOT" option get page_on_front
wp --path="$DOCROOT" option get stylesheet
```

Ожидается ядро 7.1.1, активная Twenty Twenty-Five 1.5, три активных плагина:
`carousel-block` 2.1.5, `wp-seopress` 10.2 и `wp-super-cache` 3.1.3; главная **67**, stylesheet
**twentytwentyfive**. Ядро en_US, язык интерфейса ru_RU — это штатный вариант.
MU-плагинов и CSS в Customizer нет. Единое голубое состояние наведения для кнопок и
вкладок находится в штатных Global Styles WordPress (раздел CSS редактора сайта).
Не активировать другую тему и не создавать
главную заново: это изменит восстановленные шаблоны/стили.

SEO-XML-модуль остаётся отключён, карты обслуживает ядро. Проверить:

```sh
wp --path="$DOCROOT" option get seopress_toggle --format=json
```

`toggle-titles=1`, `toggle-social=1`, **`toggle-xml-sitemap=0`**. Не включать второй
SEO-плагин. Не повторять первоначальную настройку SEOPress поверх импортированных
данных. Вся SEO-конфигурация уже в базе.

## 8. Права и безопасность только для SkySend

Администратор назначает владельца и группу **только нового `$DOCROOT`**:
PHP должен читать `wp-config.php` и сайт, писать в `wp-content/uploads` и
**только внутри** `wp-content/cache` после включения страничного кеша;
core/plugins/themes не должны быть доступны на запись другим сайтам.
Предпочтительно отдельный системный пользователь/PHP-FPM-пул SkySend.
Не применять Ubuntu-пользователя `www-data` вслепую, `chmod 777` или рекурсивный
`chown` общего `/usr/local/www`. Схема владельцев зависит от существующей изоляции.

Закрыть HTTP-выдачу wp-config, скрытых файлов, SQL, архивов, логов и резервных копий;
запретить выполнение PHP в uploads. Не открывать directory listing. Обновления
ядра/плагинов выполняются по политике компании; если PHP не пишет в core/plugins,
их обновляет администратор, а не меняет права всего jail ради обновления из GUI.

## 9. Подключить только виртуальный хост SkySend и HTTPS

Использовать существующий Apache/PHP-обработчик. У SkySend отдельный ServerName,
ServerAlias www и DocumentRoot нового `$DOCROOT`, свои логи. Должны работать
mod_rewrite и PHP; для поставленной `.htaccess` нужны согласованные AllowOverride
FileInfo/Options/AuthConfig либо перенос правил непосредственно в vhost.

В `site/.htaccess` уже сохранены WordPress-маршруты, запрет листинга/выдачи config,
14 вариантов старых `/participants/...` → `/#participants` и старая карта
`/wp-sitemap-skysend-1.xml` → `/wp-sitemap-posts-page-1.xml`.
Конфигурацию Ubuntu из Git не копировать: `${APACHE_LOG_DIR}`, a2ensite и systemd
не являются инструкцией для FreeBSD.

Если используется Nginx, он **не читает `.htaccess`**. Администратор переносит
WordPress try_files, оба типа старых 301 и защитные правила в свой server/location.
Особенно проверить несуществующие файлы и PHP-обработчик, чтобы не отдавать код PHP.

HTTPS должен иметь действующий сертификат для skysend.ru и www.skysend.ru.
Настроить HTTP → основной HTTPS и www → выбранный основной домен. Если HTTPS
завершается на прокси, корректное определение HTTPS в PHP согласовать с администратором:
доверять forwarded-заголовкам **только доверенному прокси**, не любому клиенту.
Это предотвращает циклы redirect и неверный URL редактора.

Проверить конфигурацию до применения. Для Apache на FreeBSD-хосте:

```sh
jexec www apachectl configtest
```

Только после Syntax OK и согласования применения:

```sh
jexec www apachectl graceful
```

Для Nginx аналогично `nginx -t`, затем `nginx -s reload` внутри jail. Не делать
stop/restart всего jail/общего PHP и не отключать соседние виртуальные хосты.

## 10. Проверить до переключения домена

В этом сценарии `NEW_URL=https://skysend.ru`, поэтому проверять именно **skysend.ru**
на новой точке входа через hosts/`curl --resolve`, без изменения общего DNS.
Другой тестовый hostname без замены URL может перенаправить на прежний боевой сайт.
Если компания выберет отдельный staging-домен, ему нужен соответствующий `NEW_URL`
и повторная штатная замена staging → production перед запуском.
Пример после подготовки сертификата:

```sh
curl --resolve skysend.ru:443:NEW_FRONT_IP https://skysend.ru/
```

`NEW_FRONT_IP` заменить на согласованный внешний IP. Не использовать `-k` как
замену корректного HTTPS. Не предполагать, что адрес хоста gw1 совпадает с адресом
внешнего прокси/jail; это определяет администратор.

В обычном Chrome/Edge проверить:

- главную, три баннера/автопрокрутку, кнопки, раздел партнёров и остальные модули;
- категории провайдеров слева и переключение логотипов;
- отсутствие пропавших картинок, горизонтального переполнения и mixed content;
- вход в `/wp-admin/`, редактирование страницы 67, загрузку изображения;
- футер, шапку и стили через редактор сайта; ничего не пересоздавать ради проверки;
- 301 старых партнёрских адресов и настоящий 404 неизвестного адреса.

Сохранение пробной правки проверять на черновике/ревизии и возвращать утверждённый
контент. Проверка файла/SQL внутри пакета не заменяет эти проверки на целевом jail.

### Включить кеш готовых страниц после проверки сайта

Плагин WP Super Cache находится в пакете, но кеш-файлы, `advanced-cache.php` и
`wp-cache-config.php` намеренно не переносятся: они зависят от пути и домена.
После корректной замены URL и проверки сайта администратор должен выделить
**только SkySend** отдельный каталог `$DOCROOT/wp-content/cache`, доступный на запись
PHP-пользователю этого сайта. Не открывать на запись весь `wp-content` или общий jail.
Определить фактического PHP-пользователя и проверить права `wp-config.php`:
он должен быть читаем этим пользователем. При использовании WP-CLI от root
файл конфигурации может сменить группу на `root`; после команд вернуть группу
по политике сайта. Сначала сделайте снимок БД и `wp-config.php` в закрытом месте.

Ниже `wp` запускается от пользователя сайта. Если используется root, добавить
`--allow-root`. Реактивация создаёт конфигурацию кеша **на целевом сервере**:

```sh
wp --path="$DOCROOT" plugin deactivate wp-super-cache
wp --path="$DOCROOT" plugin activate wp-super-cache
wp --path="$DOCROOT" config get WP_CACHE
wp --path="$DOCROOT" eval 'wp_cache_setting("wp_cache_clear_on_post_edit", 1); wp_cache_setting("wp_cache_not_logged_in", 2); wp_cache_setting("wp_cache_no_cache_for_get", 1); wp_cache_setting("cache_max_time", 1800); wp_cache_enable();'
```

`WP_CACHE` должен вернуть `true` или `1`. Если константа не создана при активации,
администратор задаёт её через `wp config set WP_CACHE true --raw` и снова проверяет
чтение `wp-config.php` PHP-пользователем. Кеш должен храниться только в новом
`$DOCROOT/wp-content/cache`; все вложенные каталоги, созданные WP-CLI от root,
нужно передать PHP-пользователю **в пределах именно этого каталога**.

Проверить анонимную главную **дважды**: оба ответа HTTP 200, второй быстрее;
в HTML второго ответа есть метка `Cached page generated by WP-Super-Cache`.
Карусели, категории провайдеров, SEO-теги и ссылки должны быть на месте.
Запросы с авторизацией, `/wp-admin/`, предпросмотр и XML-карта не должны получать
публичную кеш-копию. После сохранения страницы 67, шапки/футера или стилей
убедиться, что кеш очищается. После ручной смены домена, SEO-настроек или
медиафайлов очистить его явно:

```sh
wp --path="$DOCROOT" eval 'wp_cache_clear_cache();'
```

Холодный запрос всё ещё выполняет WordPress; кеш ускоряет повторные анонимные
просмотры. Если активация привела к HTTP 500, сразу отключить плагин через
WP-CLI, проверить права `wp-config.php` и журнал PHP. Не сравнивать время 500 с
временем рабочей страницы.

## 11. robots, индексация, DNS и итоговая проверка

После успешной закрытой проверки восстановить разрешённую индексацию:

```sh
wp --path="$DOCROOT" option update blog_public 1
wp --path="$DOCROOT" rewrite flush
```

Для основного URL `https://skysend.ru` установить предоставленный robots:

```sh
cp "$PACKAGE/robots-production.txt" "$DOCROOT/robots.txt"
```

При другом основном домене строку Sitemap адаптировать к `$NEW_URL`.
Robots не должен указывать на IP тестовой ВМ. Карту не создавать вручную:
`/wp-sitemap.xml` и `/wp-sitemap-posts-page-1.xml` штатные.

Перед DNS, на новой точке входа по hosts/--resolve, проверить HTTP 200 карт и
правильные XML loc. Затем администратор согласованно переключает только нужные
A/AAAA/www или upstream внешнего прокси. Если внешний адрес уже правильный,
DNS не менять. Проверить актуальные DNS-записи в момент запуска; не затрагивать MX,
почтовые TXT и другие домены. Старый сайт/БД оставить для отката.

После переключения проверить из внешней сети:

1. Главная 200, один H1/title/meta description/canonical основного HTTPS-домена.
2. OG/X и Organization/WebSite JSON-LD используют основной URL и доступные картинки.
3. robots.txt 200, Sitemap HTTPS; у главной нет noindex.
4. Обе XML-карты 200, правильный XML, только опубликованная главная;
   обе служебные XSL 200. Черновики/удалённые партнёрские страницы не индексируются.
5. Старые партнёрские адреса 301, старая карта 301, неизвестный адрес 404/noindex.
6. Редактор, медиатека, шапка/футер, карусель/вкладки работают; журналы без новых ошибок.
7. HTTP/www перенаправляются корректно; нет старого IP в src/href/SEO и mixed content.

Закрыть тестовую копию на 31.129.98.28 от индексации отдельно, после принятия нового
сайта и согласования владельца. В кабинетах владельца Search Console/Яндекс Вебмастер
отправить `https://skysend.ru/wp-sitemap.xml` и проверить фактическую индексацию.
Наличие метатегов не гарантирует немедленную индексацию или позиции.

## 13. Откат и закрытие работ

При сбое вернуть прежний docroot/upstream/vhost и, если менялись, прежние DNS.
Проверить конфигурацию и применить graceful reload. Не удалять новый или старый
сайт/БД автоматически и не восстанавливать общий jail из чужой БД. При важных
правках на новом сайте согласовать сохранение данных перед откатом.

После приёмки назначить регулярную резервную копию **новой базы + uploads**,
порядок обновлений и владельца администраторской учётки. Убрать архив и SQL из
общедоступных мест; закрытая резервная копия хранится по политике компании.

[rewrite flush](https://developer.wordpress.org/cli/commands/rewrite/flush/),
