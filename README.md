# SkySend на стандартных блоках WordPress

Лендинг рассчитан на WordPress 7.1 и официальную блочную тему **Twenty Twenty-Five**
(`twentytwentyfive`). Страница, шапка, футер и оформление хранятся в базе данных
WordPress как стандартные блоки, части шаблона и настройки «Стили». Для работы
сайта не нужны плагины, собственная тема, блок Custom HTML или добавленные
PHP/CSS/JavaScript. CSS/JavaScript самого ядра и официальной темы остаются штатными.

Инфраструктура: Ubuntu, Apache, PHP 8.3+ и MariaDB.

Версия на встроенных блоках опубликована 17.09.2026 на http://31.129.98.28/.
Результаты проверок, инструкция редактора и открытая ошибка sitemap WordPress 7.1:
[отчёт о переходе](docs/native-wordpress-20260917.md). Исправление sitemap ожидает
официального стабильного обновления 7.1.1; отложенная проверка согласована.

## Структура

- `wordpress/native-blocks` — контент, разовый импорт в медиатеку и сборщик
  сериализованных стандартных блоков; это не runtime-плагин и не тема;
- `wordpress/wp-content/themes/skysend` — сохранённая предыдущая реализация и
  источник изображений для первоначального импорта; установщик её не активирует;
- `wordpress/public` — `robots.txt` и правила Apache;
- `deploy/wordpress` — базовая установка WordPress и настройка сервера;
- `docs` — история требований и проверок предыдущих редакций;
- React-прототип в корне — история первой версии, действующим сайтом не используется.

`media.json`, `page.html`, `header.html`, `footer.html` и другие результаты сборки
содержат ID медиатеки и URL конкретной WordPress-базы. Готовые файлы из репозитория
нельзя слепо импортировать в другую базу: сначала получите её `media.json` и
пересоберите блоки.

## Базовая установка

Из корня переданного на сервер репозитория:

```bash
sudo bash deploy/wordpress/install-wordpress.sh \
  wordpress/wp-content/themes/skysend \
  wordpress/public \
  http://31.129.98.28
```

Первый аргумент — только источник сохранённых изображений, а не выбор активной
темы. Скрипт устанавливает Apache, MariaDB, PHP, последний стабильный WordPress и официальную
Twenty Twenty-Five. На новой базе активируется стандартная тема, но сам лендинг
создаётся отдельным разовым импортом ниже. Учётные данные администратора остаются
только на сервере в `/root/skysend-wordpress-admin.txt` с правами `0600`.

На существующей базе установщик не импортирует страницу и не перезаписывает
редакторские шаблоны, шапку, футер или стили. До миграции действующая тема остаётся
активной до отдельного шага `activate`; после миграции состояние защищено опцией
`skysend_native_migration_complete`. Старую `skysend` установщик не активирует
никогда. Перед запуском всегда указывайте действующий URL сайта третьим аргументом.

## Разовый переход: media → build → prepare → QA → activate

Сначала сохраните резервную копию базы, uploads и серверной конфигурации. Команды
WP-CLI ниже выполняются на целевой WordPress-базе из корня репозитория. `import.php`
запускается только вручную через WP-CLI: его нельзя помещать в `plugins`,
`mu-plugins` или подключать к работающей теме.

1. Импортируйте исходные изображения в **медиатеку целевого экземпляра**:

   ```bash
   sudo wp eval-file wordpress/native-blocks/import.php media \
     --path=/var/www/skysend --allow-root
   ```

   Будет записан `wordpress/native-blocks/media.json` с реальными ID и URL этой базы.
   При запуске под root импорт задаёт www-data владельцем файлов изображений и
   каталогов даты внутри uploads, чтобы Apache мог читать их, а медиатека — изменять.

2. Соберите блоки с помощью Node.js 22+ и временной зависимости `jsdom`:

   ```bash
   SKYSEND_BUILDER_DIR="$(mktemp -d -t skysend-native-builder.XXXXXX)"
   npm install --prefix "${SKYSEND_BUILDER_DIR}" --no-audit --no-fund jsdom@26.1.0
   SKYSEND_JSDOM="${SKYSEND_BUILDER_DIR}/node_modules/jsdom" \
     SKYSEND_ORIGIN="http://31.129.98.28" \
     node wordpress/native-blocks/build.mjs
   ```

   `SKYSEND_ORIGIN` — адрес целевого WordPress 7.1 без завершающего `/`.
   Сборщик использует штатные сериализаторы блоков этого ядра. `jsdom` нужен только
   на машине сборки, не добавляется в зависимости сайта и не работает на фронтенде.
   Если сборка выполняется локально, сначала заберите целевой `media.json`, затем
   передайте полученные HTML/JSON обратно в тот же каталог на сервере.

3. Подготовьте черновик и стандартные шаблоны, не переключая работающую тему:

   ```bash
   sudo wp eval-file wordpress/native-blocks/import.php prepare \
     --path=/var/www/skysend --allow-root
   ```

4. Выполните QA в безопасном предпросмотре стандартной темы или на копии базы:
   `validation.json` должен иметь `invalid: 0`; проверьте все блоки, изображения,
   ссылки, якоря, телефон/почту, мобильное меню, три баннера и шесть категорий
   провайдеров. В блоках не должно быть Custom HTML/shortcode и неполадок
   «восстановить блок». Не должно быть активных или MU-плагинов и дополнительного
   пользовательского CSS. Проверьте также 301 старых партнёрских адресов, настоящий
   404 неизвестного адреса, `robots.txt`, canonical и HTTP 200 карты сайта.

5. Только после проверки опубликуйте страницу и переключите тему:

   ```bash
   sudo wp eval-file wordpress/native-blocks/import.php activate \
     --path=/var/www/skysend --allow-root
   ```

   Затем повторите проверку действующего сайта. `prepare` и `activate` запрещают
   повторный импорт после `skysend_native_migration_complete`, чтобы не стереть
   изменения, сделанные в редакторе. Не удаляйте этот маркер ради повторного запуска.
   До публикации повторный `prepare` также отказывается перезаписывать объект,
   содержимое которого изменено после последнего импорта.

## Где дальше редактировать

- **Страницы → SkySend — система приёма платежей**: тексты, изображения, баннеры,
  партнёры, показатели, программы и категории провайдеров;
- **Внешний вид → Редактор → Паттерны → Все части шаблона**:
  «SkySend — Шапка» и «SkySend — Футер»;
- Меню: стандартный блок **Навигация** внутри «SkySend — Шапка»;
- **Внешний вид → Редактор → Стили**: цвета, типографика и отступы без добавления CSS.

Возраст компании и год копирайта теперь обычный редактируемый текст. Обновляйте
год ежегодно, а количество полных лет работы — 15 мая; автоматически PHP их больше
не рассчитывает. Данные оборота и транзакций не становятся новыми от смены года.

Категории провайдеров используют штатные **горизонтальные вкладки WordPress 7.1**.
Три баннера переключаются вручную тем же нативным механизмом. Старых автопрокрутки,
свайп-карусели и reveal-анимаций нет: собственный JavaScript не перенесён.

Сохраняются базовые возможности ядра: title, canonical, robots и XML sitemap.
Произвольные meta description, Open Graph/Twitter и Organization JSON-LD раньше
создавала кастомная тема; стандартные контентные блоки их не добавляют. При данном
ограничении «без плагинов и custom runtime-кода» эти дополнительные SEO-теги
**не перенесены**. Нельзя считать обычный абзац заменой метатега или вставлять
JSON-LD через Custom HTML.

## Другой или переустановленный сервер

Одного `git clone` недостаточно для уже отредактированного native-сайта: его
содержимое находится в стандартной базе WordPress и uploads. Для восстановления
переносите согласованную полную базу и медиатеку вместе с официальной темой,
сохраняя взаимосвязи ID и штатно заменяя URL. Альтернатива на чистой базе — заново
пройти всю цепочку `media → build → prepare → QA → activate` с её собственными ID.
Нельзя импортировать старый `media.json`/HTML в пустую базу и ожидать совпадения ID.

После переноса DNS замените WordPress `home`/`siteurl` и URL sitemap на HTTPS,
выпустите TLS-сертификат и повторите проверку. Базовый установщик не выполняет
перенос базы, итоговое согласование или переключение DNS автоматически.
